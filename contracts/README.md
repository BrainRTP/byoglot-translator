# Shared contracts

TypeScript in `lib/` is the reference implementation. Data and fixture expectations in `contracts/` are generated from it with `UPDATE_CONTRACTS=1 pnpm test tests/unit/contracts` and checked by `pnpm test`. A native implementation loads the same files in its own tests and must produce `expected` for every `input`.

A behavior change belongs in one pull request containing the TypeScript change, regenerated contract files and every native implementation that exists at that time.

Fixture files have the format `{ "contract": string, "version": number, "cases": [{ "name": string, "input": any, "expected": any }] }`. Segment ids are canonical non-negative integers written as strings. Sort them as numbers to reproduce JavaScript object key order. A repeated id in a model response uses the last value, as in `JSON.parse`. Every JSON file uses two-space indentation and a trailing newline. The harness checks the contract name and version, preserves hand-authored input key order and prints each changed case name during an update. The two id-order inputs deliberately list numeric keys out of order; expected prompts and failed ids still use numeric order.

String lengths are UTF-16 code units, as in JavaScript `String.length`. `limits.json` sets `maxEditorText` to 20000 for editor input, alongside `maxSelection` and `maxContext`. The compact `JSON.stringify` output is part of the page prompt: there is no space after `:` or `,`, `/` and non-ASCII characters are not escaped, and control characters are escaped as `\b \f \n \r \t` or `\u00xx` with lower-case hex. U+2028 and U+2029 stay unescaped. Lone UTF-16 surrogates are escaped with lower-case hex, for example `\ud83d`.

Language profiles are not copied here. They live in `lib/translate/profiles/<code>.md`; native builds bundle those files as resources. The profile id is the file name without `.md`, and the profile text is the trimmed file content.

Language prompt names use `languages.json`: `auto` selects its `auto` text, known codes use `names[code]`, and off-list codes, including region codes such as `pt-BR`, use the code itself. Prompt language names come only from this fixed table, without a locale-dependent display-name lookup. The `codes` array preserves picker order.

Provider responses that do not match the expected JSON shape have kind `incompatible` and the fixed detail `unexpected response shape`, independent of the validator library. The provider backend logs the full validator message with `console.warn` for endpoint diagnostics.

Provider completion content accepts a string, null or an array of chunks; only chunks with `type: "text"` contribute their `text`, joined in order, and an array without text chunks is an empty completion. A null model name falls back to its id. OpenAI has no automatic default model; Mistral uses the first model whose `capabilities.completion_chat` is not false, or no default if every model is explicitly non-chat.

`Retry-After` is trimmed before parsing. Seconds must match `[0-9]+(\.[0-9]+)?`: a non-negative decimal integer or fraction, without a sign, exponent or hexadecimal prefix. Multiply by 1000 and round to the nearest millisecond. A date must be an IMF-fixdate HTTP date, for example `Thu, 01 Jan 2026 00:00:10 GMT`, with English weekday/month names, GMT and a valid calendar date. Its delay is the date minus the current time, clamped to zero. Both forms are capped at 86400000 milliseconds (24 hours); values above the cap, including decimal-seconds values too large for a finite number, become the cap. Other values, including `-1`, are ignored. RFC 850 and asctime dates and exponent numbers such as `1e3` are ignored. Provider error cases with a `now` input use that ISO timestamp as the fixed current time when computing date delays.

`samples/export-v1.json` is a raw portable export sample, outside the fixture envelope. Tests validate it with `parseExport` and with the published JSON Schema through the installed Zod `fromJSONSchema` conversion. Parsing and schema validation reject unknown keys, including nested connection secrets. `buildExport` explicitly picks portable fields and drops unknown stored keys before strict validation.

The export format contains portable globals, templates, profile overrides, site rules and provider connections without secrets. It excludes opencode connections. Native apps ignore `siteRules`. Model references keep `connectionId`; an importer drops references whose connection id is absent from `connections`. Export and import controls are a separate change. Older clients reject export-v1 files containing the `openai` or `mistral` preset with their existing format error.
